# UnrealDash Toolchain Research - 2026-09-15

## Key Takeaways

- Current Epic Games Launcher release is UE 5.8 (announced 2026-06-17, available 2026-06-23; hotfixes 5.8.1 and 5.8.2 since), and Epic has stated 5.8 is the last planned major UE5 release before UE6. [unrealengine.com](https://www.unrealengine.com/news/unreal-engine-5-8-is-now-available)
- UE 5.8 officially requires the full Visual Studio 2022 (17.14+) or VS 2026 (18.0+) IDE with "Desktop development with C++" and "Game development with C++" workloads; Epic's own documentation does not mention or endorse a Build Tools-only install. [dev.epicgames.com](https://dev.epicgames.com/documentation/unreal-engine/setting-up-visual-studio-development-environment-for-cplusplus-projects-in-unreal-engine)
- UE 5.8 MSVC requirement: minimum toolset 14.38, recommended 14.50; Windows SDK minimum 10.0.22621.0, recommended 10.0.26100 or newer - so the 14.44/10.0.26100 combination in the brief falls inside the supported range. [dev.epicgames.com](https://dev.epicgames.com/documentation/unreal-engine/setting-up-visual-studio-development-environment-for-cplusplus-projects-in-unreal-engine)
- UE 5.8 Android toolchain (Turnkey-pinned): Android Studio Koala 2024.1.2 Patch 1, NDK r27c, JDK OpenJDK 21.0.3, target SDK 35 recommended / SDK 34 minimum for compilation, minimum installable API 26, device minimum OpenGL ES 3.2 / Vulkan 1.1 (Android 10+). SetupAndroid.bat still ships under Engine/Extras/Android but Turnkey is now the documented/automated path. [dev.epicgames.com](https://dev.epicgames.com/documentation/unreal-engine/android-development-requirements-for-unreal-engine)
- Unisoc UIS7870 (A7870): 8-core big.LITTLE (1x Cortex-A76 @2.7GHz + 3x A76 @2.3GHz + 4x A55 @2.1GHz), Mali-G57 GPU (4 cores, up to 850MHz, Valhall architecture), 6nm process. Mali-G57 (Valhall gen 1) tops out at Vulkan 1.1, not 1.2/1.3. [unisoc.com](https://www.unisoc.com/en/solution/IGCockpitSolutionUS/A7870) / [arm.com](https://developer.arm.com/Processors/Mali-G57) (low-confidence retailer figures noted separately in Q3)
- Mali GPU + UE Vulkan crashes are an active, recurring class of bug on Epic's own bug tracker/forums (Mali-G76 shader-compile crash on 5.8, random Vulkan RHIThread crashes on Mali in 5.6) - this is a live risk for a UIS7870/Mali-G57 target, not a hypothetical. [forums.unrealengine.com](https://forums.unrealengine.com/t/ue-5-8-vulkan-crash-on-mali-g76-libgles-mali-so-ue-5-4-4-works/2737388)
- For JSON Schema validation in a UE module: nlohmann/json + pboettch/json-schema-validator (MIT, draft-7) is the most common pairing, but nlohmann/json pulls in `std::any`, which requires RTTI - and UE disables RTTI by default, so the module needs `bUseRTTI = true` in Build.cs (or a fork avoiding `std::any`). Exceptions must also be reconciled since UE builds with exceptions off by default. [github.com/nlohmann/json issue #3900](https://github.com/nlohmann/json/issues/3900)
- valijson (header-only, MIT-style, draft-7, C++17) is parser-agnostic and can sit on top of UE's own JSON types or RapidJSON without requiring RTTI/exceptions from nlohmann. RapidJSON's own schema.h only validates draft-4. jsoncons is the only header-only candidate with 2020-12 draft support. Unreal's built-in FJsonObject/JsonUtilities has no JSON Schema validation of any kind. [github.com/tristanpenman/valijson](https://github.com/tristanpenman/valijson)
- UE 5.8's pinned Linux cross-compile toolchain is v26 (clang 20.1.8, Rocky Linux 8 base); v24/clang-19 is explicitly flagged by the community as broken for 5.6/5.7. [dev.epicgames.com](https://dev.epicgames.com/documentation/unreal-engine/linux-development-requirements-for-unreal-engine?lang=en-US)
- WSL2 Vulkan via Mesa "dzn" (Vulkan-over-D3D12) is real but partial in 2026: it works on some Intel/AMD iGPUs at a ~30% perf penalty and is explicitly non-conformant/"testing only"; it does not work at all on some ARM64/other GPUs (falls back to llvmpipe software rendering). A UE Linux smoke test under WSL2 is plausible on x86-64 desktop GPUs but is not a reliable substitute for a real Linux box/VM for the actual target validation. [github.com/microsoft/wslg](https://github.com/microsoft/wslg/issues/1470)
- For an embeddable WASM host targeting Android ARM64 + Windows x64 + Linux x86-64: WAMR (Apache-2.0 + LLVM exception) is the only one of the three offering interpreter, AOT, and JIT modes with a small footprint and built-in instruction-count metering; wasm3 (MIT) is interpreter-only, smallest binary, weakest limiting API; wasmtime (Apache-2.0 + LLVM exception) has the most mature fuel-metering API but its JIT (Cranelift) is not viable on Android - only precompiled AOT (.cwasm) mode is realistic there.

## Q4: JSON Schema validation in C++ for a UE module

- **nlohmann/json + pboettch/json-schema-validator**: MIT license, validates against **JSON Schema draft-7** (v2 of the validator; v1 only did draft-4), requires nlohmann/json >=3.6.0, header-heavy but not strictly header-only (ships a small compiled source unless you vendor it as header-only). Known UE compile issue: nlohmann/json includes `std::any` when C++17 is detected, and `std::any` requires RTTI - Unreal Build Tool disables RTTI by default, so building this in a UE module needs `bUseRTTI = true;` in the module's Build.cs, or patching around `std::any`. Exceptions are a second friction point: UE also disables C++ exceptions by default (UBT does not use the exception system), while nlohmann/json throws by default; this can be worked around by defining `JSON_NOEXCEPTION` (falls back to `abort()`) or by explicitly enabling exceptions for the module. [github.com/pboettch/json-schema-validator](https://github.com/pboettch/json-schema-validator), [github.com/nlohmann/json#3900](https://github.com/nlohmann/json/issues/3900)
- **valijson**: header-only, C++17 required, MIT-style license (BSD-2-Clause per repo), validates **JSON Schema draft-7** keywords (tested against the standard JSON Schema Test Suite). It is parser-agnostic - it can bind to RapidJSON, JsonCpp, Boost Property Tree, or PicoJSON as the underlying DOM, which means it does not need to pull in nlohmann/json's RTTI/exception baggage; it can plausibly be pointed at RapidJSON as the parse layer to stay ABI-light in a UE module. No UE-specific compile issues found in this search pass. [github.com/tristanpenman/valijson](https://github.com/tristanpenman/valijson)
- **RapidJSON schema.h**: MIT license, header-only, but only validates **JSON Schema draft-4** - a real limitation if the project's schemas use newer draft keywords. [rapidjson.org](https://rapidjson.org/md_doc_schema.html)
- **jsoncons**: header-only, and per its own docs supports **drafts 4, 6, 7, 2019-09, and 2020-12** - the broadest draft coverage of the four candidates. License and UE-specific build-flag issues were not independently confirmed in this pass (unverified whether it hits the same RTTI/exceptions friction as nlohmann; check before adopting). [github.com/danielaparker/jsoncons](https://github.com/danielaparker/jsoncons/blob/master/doc/ref/jsonschema/jsonschema.md)
- **Unreal's built-in FJsonObject / JsonUtilities**: confirmed to have **no JSON Schema validation**. `FJsonObjectConverter` (in the JsonUtilities module) converts between `FJsonObject` and UStructs (`JsonObjectToUStruct`, `UStructToJsonObjectString`) and offers a `bStrictMode` flag plus an `OutFailReason` string for structural conversion failures, but this is UStruct-reflection-based type/field checking, not schema validation against an external JSON Schema document. [dev.epicgames.com](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/JsonUtilities/FJsonObjectConverter)
- General UE build-system note applicable to all four candidates: RTTI and C++ exceptions are both off by default in UnrealBuildTool; any library assuming either is on (nlohmann/json via `std::any` is the confirmed case here) needs explicit Build.cs overrides (`bUseRTTI`, `bEnableExceptions`) or source patching.

## Q5: Linux packaging from Windows in UE 5.8

- Epic's Linux Development Requirements doc (covers UE 5.7 and 5.8) pins cross-compile toolchain **v26**, built on **clang 20.1.8**, distributed as `v26_clang-20.1.8-rockylinux8.exe` for the Windows-hosted cross-compiler and `native-linux-v26_clang-20.1.8-rockylinux8.tar.gz` for native Linux builds. Recommended host/target OS for the toolchain is Ubuntu 22.04 or Rocky Linux 8. [dev.epicgames.com](https://dev.epicgames.com/documentation/unreal-engine/linux-development-requirements-for-unreal-engine?lang=en-US)
- Community reporting (forums.unrealengine.com) flags toolchain **v24 (clang 19)** as having undefined-behavior problems specifically called out as unfit for **UE 5.6 and 5.7**, and toolchain **v25** as the one needed to avoid dependency issues on 5.6 - i.e., there is a real history of toolchain/engine-version mismatches breaking Linux cross-compiles across recent 5.x releases, so pin the exact v26/clang-20.1.8 build for 5.8 rather than reusing an older toolchain zip. [forums.unrealengine.com](https://forums.unrealengine.com/t/linux-cross-compiling-tool-chain-for-5-7/2684413)
- WSL2 as a Linux smoke-test target: Epic's own Linux docs say nothing about WSL2 specifically (unverified/no official guidance either way). Independently, WSL2's GPU-acceleration path (WSLg, using Mesa's "dzn" Vulkan-over-D3D12 driver, or the "d3d12" Mesa Gallium driver) is real but partial as of 2026:
  - Vulkan via Mesa dzn does work on some desktop iGPUs (e.g., reported working on Intel Arrow Lake-S iGPU) at roughly a 30% performance penalty versus native Windows. [github.com/ggml-org/llama.cpp discussion](https://github.com/ggml-org/llama.cpp/discussions/26729)
  - dzn is explicitly non-conformant and documented by Mesa/Microsoft as "testing use only," and current Ubuntu WSL mesa-vulkan-drivers packages (as of 26.0.3) do not even ship the dzn ICD by default, requiring manual driver installation.
  - On some hardware (e.g., ARM64 hosts with Qualcomm Adreno GPUs) GPU passthrough does not work at all and Mesa silently falls back to `llvmpipe` software rendering - i.e., failure mode is "it runs but with no GPU," not a hard error, which is a trap for smoke testing.
  - Given the target dev workstation is Windows x86-64 with a real GPU, a WSL2 smoke test for a packaged Linux UE build is **plausible for a basic launch/render check** but should not be treated as representative of real Linux/Vulkan behavior; a native Linux box or VM (with a real Vulkan ICD, e.g., an actual Mesa RADV/ANV/NVIDIA driver) is still the credible validation target before calling the Linux build "tested." [github.com/microsoft/wslg#1470](https://github.com/microsoft/wslg/issues/1470), [github.com/microsoft/wslg#1254](https://github.com/microsoft/wslg/issues/1254)

## Q6: Embeddable WebAssembly runtimes (Android ARM64 / Windows x64 / Linux x86-64)

- **WAMR (wasm-micro-runtime, Bytecode Alliance)**: license **Apache-2.0 WITH LLVM-exception**. Supports interpreter, AOT, and JIT (LLVM-JIT and a fast "Fast-JIT") execution modes - the only one of the three candidates offering all three on the same codebase. Designed for embedded/IoT with a genuinely small footprint (project literature markets it as "small footprint, high performance, highly configurable"). Execution limiting: `WAMR_BUILD_INSTRUCTION_METERING` build flag plus `wasm_runtime_set_instruction_count_limit()` caps instruction count, but this is documented as **only supported in classic-interpreter mode**, not AOT/JIT - a real constraint if the feasibility spike wants both AOT speed and hard execution caps simultaneously. Memory can be constrained via configured linear-memory limits and supports shrinking unused memory. [github.com/bytecodealliance/wasm-micro-runtime](https://github.com/bytecodealliance/wasm-micro-runtime), [wamr.gitbook.io](https://wamr.gitbook.io/document/appendix/readme)
- **wasm3**: license **MIT**. Interpreter-only (no AOT/JIT) - this is its main limitation for a host wanting near-native compute speed, but its interpreter is unusually fast for a tree-walking/bytecode design and its runtime binary footprint is small (commonly cited as tens of KB, smaller than WAMR's interpreter). Confirmed to build and run on Android among other platforms. No dedicated fuel/gas-style execution-limiting API was found in this pass beyond whatever host-side call-count/step wrappers a caller adds itself - **unverified** whether wasm3 ships a first-class metering API comparable to WAMR's instruction-count limit or wasmtime's fuel. [github.com/wasm3/wasm3](https://github.com/wasm3/wasm3)
- **wasmtime (Bytecode Alliance)**: license **Apache-2.0 WITH LLVM-exception**. Uses Cranelift (or Winch) as its JIT/AOT backend; both can run in AOT mode (precompile in one process via `wasmtime compile` to a `.cwasm` file, then load it in another) or JIT mode (compile and run in the same process). For Android specifically: Wasmtime documents Android as a supported but "less well tested" platform than its Tier-1 targets, and for genuinely constrained/no_std-style environments the Cranelift/Winch codegen backends must be disabled at build time, meaning **the module must be precompiled elsewhere and only the AOT/.cwasm loader ships on-device** - running the JIT compiler live on the Android ARM64 head unit is not the documented supported path. Execution limiting: wasmtime's **fuel** API (`Config::consume_fuel`, `Store::set_fuel`/`add_fuel`) is the most mature of the three - most instructions consume 1 unit of fuel, a Store starts at 0 fuel and traps immediately unless fuel is added, and the deterministic trap-on-exhaustion behavior is explicitly documented, making it the strongest fit if deterministic execution bounding is a spike requirement. [docs.wasmtime.dev](https://docs.wasmtime.dev/stability-platform-support.html), [docs.wasmtime.dev fuel example](https://github.com/bytecodealliance/wasmtime/blob/main/examples/fuel.rs)
- Binary size ordering (qualitative, not independently benchmarked here): wasm3 (interpreter-only) is the smallest; WAMR's interpreter-only configuration is next smallest, with AOT/JIT modes adding size for the codegen backend; wasmtime with Cranelift is the largest since it embeds a full compiler backend - which reinforces that a wasmtime deployment on the Android ARM64 head unit should plan on the AOT-only/no-Cranelift-on-device build variant rather than shipping the full JIT-capable runtime.
- Bottom line for the spike: WAMR is the only candidate with a first-party AOT+interpreter+JIT story across all three target platforms plus built-in (if interpreter-only) execution metering; wasmtime brings the strongest fuel-limiting semantics but needs an AOT-only build discipline on Android; wasm3 is the simplest/smallest but weakest on both execution-limiting API maturity and raw throughput ceiling (interpreter-only, no AOT/JIT path at all).
