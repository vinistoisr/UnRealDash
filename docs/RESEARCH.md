# Research notes and sources

Reviewed 2026-09-15. Primary sources only. Findings below are documented capabilities or constraints; the project plan's implementation choices and numerical targets are proposals. No runtime, hardware, or template has been tested as part of this research.

| ID | Finding | Project implication and source |
| --- | --- | --- |
| R1 | Epic's UE 5.8 HMI template uses UMG/viewmodels, VSS-based signals and OLink/WebSocket. Access requires a request and the article mentions Perforce access. | Useful architectural reference; do not require gated code or repeat vendor performance claims as our results. [Epic HMI announcement](https://www.unrealengine.com/news/unreal-engine-hmi-template-available-now) |
| R2 | Unreal build/cook/package operations compile executable code and prepare content for a target platform. | Distinguish portable data edits, cooked content, and application updates. [Packaging documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project) |
| R3 | FImageUtils exposes runtime import of a texture file as a transient Texture2D. | Supports testing external raster assets without the editor; memory, formats, and stalls need actual measurement. [API reference](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FImageUtils/ImportFileAsTexture2D) |
| R4 | Epic recommends event-driven UMG updates, judicious invalidation and limited Tick/attribute polling. | Use a signal registry and explicit UI notifications. Profile animated components separately. [UMG optimization](https://dev.epicgames.com/documentation/en-us/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine) |
| R5 | Pixel Streaming sends rendered output from a desktop/server Unreal process to an interactive browser frontend using WebRTC. | Remote authoring preview is feasible but still needs a rendering host. It is not the in-car rendering architecture. [Pixel Streaming](https://dev.epicgames.com/documentation/unreal-engine/pixel-streaming-in-unreal-engine) |
| R6 | COVESA VSS defines a signal description system/catalog independently of transport. | Reuse vocabulary with custom namespaces; implement vehicle-specific mapping separately. [VSS project](https://github.com/COVESA/vehicle_signal_specification), [VSS documentation](https://covesa.github.io/vehicle_signal_specification/) |
| R7 | Linux SocketCAN exposes CAN through the networking/socket infrastructure and documents virtual CAN interfaces. | Useful for Linux adapters and repeatable virtual-bus integration tests. [Linux kernel documentation](https://www.kernel.org/doc/html/latest/networking/can.html) |
| R8 | cantools provides CAN database parsing, decoding/encoding, and C source generation, under MIT. | Candidate offline validation and fixture tool; evaluate supported DBC constructs before deciding runtime reuse. [cantools repository](https://github.com/cantools/cantools) |
| R9 | Compatibility import is a proposed investigation, not an established feature. | Evaluate user-supplied reference media and documented signal formats individually; do not imply support for proprietary project files. |
| R10 | ELM documents its OBD interpreter and request/response commands. | An OBD connector is separate from raw CAN decoding; assess polling throughput on the chosen adapter. [Manufacturer documentation](https://www.elmelectronics.com/products/ics/obd/) |
| R11 | Android USB host support includes discovery and permission handling; Bluetooth permissions differ by Android version and operation. | Cross-platform rendering does not provide adapters automatically. Build and test platform integration. [USB host](https://developer.android.com/develop/connectivity/usb/host), [Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions) |
| R12 | Epic documents Android ARM64 and compatible graphics APIs/GPUs, with toolchains tied to engine versions. | Validate a specific device and pin its build toolchain. Do not infer that every Android head unit qualifies. [Android setup](https://dev.epicgames.com/documentation/unreal-engine/android-quick-start) |
| R13 | Epic documents Linux x86-64 toolchains and Vulkan requirements. | Qualify desktop Linux separately from ARM Linux boards. [Linux requirements](https://dev.epicgames.com/documentation/en-us/unreal-engine/linux-development-requirements-for-unreal-engine) |
| R14 | Epic's EULA separates project ownership from engine licensing, restricts Engine Tools distribution, and lists incompatible license combinations. Commercial obligations depend on distribution and use. | Select a compatible original-code license and resolve authoring/build distribution terms before release. This research does not establish a legal classification for the future product. [Unreal EULA, sections 3–7](https://www.unrealengine.com/eula/unreal) |
| R15 | Niagara supports effect types and scalability controls at several levels. | Budget effects by device profile and measure representative scenes, rather than removing advanced visuals from the architecture. [Niagara scalability](https://dev.epicgames.com/documentation/unreal-engine/scalability-and-best-practices-for-niagara) |
| R16 | Unreal documents differing feature support across mobile rendering paths. | Maintain explicit capability requirements and visual fallbacks for advanced materials and effects. [Rendering feature reference](https://dev.epicgames.com/documentation/unreal-engine/rendering-features-reference) |
| R17 | Unreal distinguishes world-space widgets from screen-space widgets, which are not occluded by the world. | Use 3D presentation where beneficial while retaining a crisp overlay for important values. [Widget space API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/UMG/EWidgetSpace) |
| R18 | MegaSquirt publishes distinct serial, 11-bit broadcast, and proprietary 29-bit CAN documentation. | Version profiles explicitly; start with broadcast decoding and supplied firmware details. [Manual index](https://www.msextra.com/manuals/), [broadcast specification](https://www.msextra.com/doc/pdf/Megasquirt_CAN_Broadcast.pdf) |
| R19 | usb-serial-for-android supplies Android USB serial drivers for specified chipsets and devices. | Candidate transport component only when the actual USB interface matches; not a generic CAN decoder. [Maintainer repository](https://github.com/mik3y/usb-serial-for-android) |
| R20 | OBDLink's CX documentation identifies it as a BLE adapter, illustrating device-specific transport differences. | Validate BLE profiles separately from Bluetooth Classic connections. [Vendor support](https://support.scantool.net/support/solutions/articles/43000746707-obdlink-cx-adapter-notes) |

## Important uncertainties

No actual device minimum, application size, frame rate, cold-start time, CAN coverage, or AI editing success rate has been established. A published API is not proof of acceptable shipping performance. The HMI template was not downloaded or inspected, and no access request was submitted. Browser Studio is a proposed custom application, not Unreal Editor compiled to run in a browser. Cloud operation and primary-cluster deployment need separate assessment once their scope is concrete.

## Local pilot evidence

The owner's Scirocco repository was inspected read-only: top-level architecture, board USB boot configuration and encoder, deck relay/parser and schema decoder, simulator, runbook, and engine-channel findings. These identify the hardware and the integration boundary summarized in [Pilot integration](PILOT-INTEGRATION.md). No code/assets were imported and no vehicle was contacted. Existing documentation contains historical configuration differences, so repository findings must be checked against deployed revisions before hardware testing.
